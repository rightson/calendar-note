# Calendar-Note development and QA

Calendar-Note 0.1.0 targets desktop Obsidian 1.14.5 and later. Desktop-only describes the verified release scope; mobile behavior has not been tested. The native QA below was performed in an isolated Obsidian 1.14.5 Vault. Automated tests cover core logic through adapters and fixtures, so they do not establish every native UI behavior. See the [0.1.0 release notes](../releases/0.1.0.md) for a concise public summary and [releasing](RELEASING.md) for packaging and release steps.

Calendar-Note now has a local Obsidian plugin implementation. The HTML pages under `docs/changes/calendar-note/preview/` remain a separate browser prototype: they use browser storage and fictional sample feeds, and do not inspect or modify a Vault.

## Build and package

Requirements: Node.js 22 or newer, npm, and `zip` for packaging.

```sh
npm ci
npm run typecheck
npm test
npm run build
npm run package
```

`npm run build` writes the plugin bundle to the repository root as `main.js`. `npm run package` rebuilds it and creates `dist/calendar-note.zip`, containing the `calendar-note/` directory with `main.js`, `manifest.json`, `styles.css`, `LICENSE`, and generated `THIRD_PARTY_LICENSES.txt`.

For day-to-day development, `npm run dev` rebuilds into a Vault on every save:

```sh
npm run dev -- /absolute/path/to/Vault
# or: export CALENDAR_NOTE_VAULT=/absolute/path/to/Vault; npm run dev
```

It writes `main.js` (with an inline source map) to `<Vault>/.obsidian/plugins/calendar-note/` each time a source file changes, copies `manifest.json` and `styles.css` when they change, and leaves the last good `main.js` in place when a build fails. The path must be absolute (a leading `~` is expanded) and contain a `.obsidian` folder; unlike the test installer, any Vault is accepted, so prefer a test Vault for unreleased code. It also adds an empty `.hotreload` file to the plugin folder: with the [Hot Reload](https://github.com/pjeby/hot-reload) community plugin installed, Obsidian reloads Calendar-Note after each build; without it, turn the plugin off and on in **Settings → Community plugins**. Plugin data (`data.json`) is never touched. Stop it with Ctrl+C.

For a dedicated test Vault, build first and use an explicit absolute path:

```sh
npm run install:test-vault -- /absolute/path/to/calendar-note-test-vault
```

The installer requires an existing directory with `test` in its name and writes to that Vault's `.obsidian/plugins/calendar-note/`. It will not install to the repository or a directory without `test` in its name. To install manually, extract the archive's `calendar-note/` folder into `<TEST_VAULT>/.obsidian/plugins/`. In Obsidian enable community plugins and Calendar-Note under **Settings → Community plugins**, then reload if prompted.

Uninstall by disabling Calendar-Note and removing its plugin folder. `data.json` inside that folder stores plugin settings, source/cache/history, and note-link tracking; `recovery.json` stores any interrupted multi-file transaction. Removing the folder removes both files. Event, Daily, and Weekly Markdown files and their existing links remain in the Vault. Copy `data.json` first if you may want to preserve settings, history, or tracking state. Resolve pending recovery before uninstalling; if it cannot be resolved, keep a copy of `recovery.json` until recovery is handled. The plugin has no automatic Vault-note cleanup command.

## Plugin behavior and boundaries

The plugin registers a Calendar-Note view with Week, Day, Month, Year, Custom days, and List views. Clicking the ribbon icon opens the calendar in a new tab; Ctrl/Cmd-click opens it in a right split beside the active leaf. These actions are also available as the `open-calendar` (“Open calendar in new tab”) and `open-calendar-right` (“Open calendar in right split”) commands. Obsidian registers both commands for user-assigned hotkeys; the plugin adds no default bindings. The toolbar toggles the main calendar between All days (the default) and Workdays (Monday through Friday); the mini-calendar always retains seven days, and the setting does not change note week rules. The sidebar has a Today control beside month navigation and a keyboard-accessible resize separator. Close the expanded sidebar with its ×; a compact, keyboard-focusable icon handle at the left edge restores it when collapsed without consuming a toolbar row. Native checks confirmed the handle is accessible and restores the saved width. The main calendar can be hidden the same way with the toolbar's panel icon, and a matching handle at the right edge restores it. With the main calendar hidden, the mini calendar fills the view in as many month columns as fit; clicking a date opens its Daily Note, and a week number its Weekly Note, in one leaf beside the calendar, reused while it stays open: a new tab in the pane on the calendar's far side when one exists, else a split to the right of the calendar. Hiding one panel always shows the other, so the view is never empty. This mode has automated coverage only; it has not had native QA. Sidebar width and both collapsed states are stored in plugin settings. Two settings under **Clicking** choose what a plain click on a date does. **Clicking a date in the mini calendar** moves the main calendar to that date (the default) or also opens its Daily Note beside the calendar, in the same reused leaf, or in a new tab; with the main calendar hidden, the default opens the Daily Note beside the calendar as described above. **Clicking an empty slot in the main calendar** keeps the original behavior by default (a new event in Week, Day, and Custom days; the Daily Note in Month and Year), or always creates a new event (all-day in Month and Year and in the all-day row), opens the Daily Note beside the calendar or in a new tab, or does nothing. Clicks on date headers, day numbers, and week numbers keep opening their notes, and right-click still offers **New event**. These settings have automated coverage of their decision rules only; they have not had native QA. The **Clicking an event** setting chooses what an event click in the main calendar does: show the event details dialog (the default), open the Event Note beside the calendar in that same reused split, or open it in a new tab. The details dialog, also reachable from an event's ⋯ button, shows the calendar name, location, and description as the source calendar provides them, and an Event Note section: the note's path (a dropdown when several notes could hold the event: its Event Note and the notes in the same folder whose names start the same way, such as `Standup (2).md` beside `Standup.md`, leaving out Daily and Weekly Notes and notes held by another event; picking one binds the event to it as **Change…** does, without opening it), a read-only rendering of the note's text below its frontmatter, and three open buttons: **Left** and **Right** open the note in a new tab in the pane on that side of the calendar (the main area when that side faces it from a sidebar), splitting the calendar on that side when no pane is there, and the central, emphasized **Open in new tab** follows the new-tab placement below. This setting has automated coverage only; it has not had native QA. Notes the calendar opens in a new tab (dates and week numbers with the main calendar shown, and Event Notes) go to the calendar's far side so the calendar stays in view: with the calendar in a sidebar, a new tab in the main area; otherwise a new tab in the nearest side-by-side pane, the one to its left when there is one and else the one to its right. Panes stacked above or below the calendar are not used. With nothing beside it, the note opens in a new tab in the calendar's own group as before. This placement has automated coverage of the layout rules only; it has not had native QA. Other commands are `new-event`, `refresh`, `change-history`, `retry-recovery`, and `remove-duplicate-event-note-title` under the `Calendar-Note:` display prefix. Local event files use `event_id`, `start`, and `end` frontmatter; imported notes also track source identity and recurrence ID. Event Note body content and unrelated frontmatter are retained when managed fields change. Right-clicking the calendar opens a menu with **New event** at the pointer's time slot (09:00 on the clicked date outside time grids) and one **Edit** entry per event overlapping that slot; in an all-day row, Month, or Year cell the entries cover that date, all-day events first. The right-clicked event is always listed. Each entry opens the event details dialog. The context menu has automated coverage of its overlap rules only; it has not had native QA. The event details dialog's **Change…** control links an event to another Markdown note, or to a new note at a typed path. The chosen note gains the managed fields and its own heading or filename becomes the event title; the previous Event Note loses only the managed fields; the Daily entry is rewritten to the new link in the same transaction. A note that is already another event's Event Note, a Daily Note, has invalid YAML, or already uses a managed property name (`event_id`, `start`, `end`, `all_day`, `source`, `ical_uid`, `recurrence_id`) is refused unchanged. This control has automated coverage only; it has not had native QA. Event Notes link to a managed bullet under the Daily Note's `## Events` section (an existing `## Event` section is still used). A bullet is identified by its generated form and its link to the Event Note, so a stale time or alias is rewritten in place and repeats are removed; lines in the user's own words are never changed. Opening, creating, moving, or saving an event adds its entry back when none remains, while a background source update leaves a rewritten or removed entry alone and records a change that needs attention. The event-title input uses a vertically labeled, full-width row.

The plugin also registers a separate month calendar view (`calendar-note-months`) meant for a sidebar. With **Add to the right sidebar at startup** on (the default), it is added to the right sidebar once the layout is ready, without taking focus, only when no leaf of that view exists anywhere, so a tab the user moved keeps its place. `open-months` (“Open month calendar in sidebar”) reveals the existing view or adds one to the right sidebar; `open-months-below-explorer` (“Move month calendar below the file explorer”, also a settings button) closes any open copy and splits the left-sidebar file explorer horizontally to put the view under it, or adds a new group at the bottom of the left sidebar when no file explorer is there. The view renders one month card at each of three sizes (regular, compact, and tight rows), keeps the roomiest size that shows at least **Show at least** months (1–12, default 3), and otherwise the size that shows the most whole months, preferring the roomier one on a tie; it then adds following months while whole cards fit, in as many columns as the width allows, up to 24. Cards always have six rows so their height is stable. Dates open Daily Notes and week numbers open Weekly Notes in the main area (Ctrl/Cmd for a new tab); dots count visible events per day in the display time zone, bold dates have an existing Daily Note, and the open Daily Note is highlighted. Imported events are marked only within the range the main calendar has loaded. This view has automated coverage of its layout and placement rules and a browser render with stubbed Obsidian APIs; it has not had native QA.

### Event Note problems

Each scan records Event Note problems as structured entries rather than plain messages: **duplicates** (several notes with one `event_id`, grouped into one entry however many there are, or copies left beside the note a re-added subscription reconnected), **not in calendar**, **removed calendar** (with the current calendars that list the same iCal event when more than one does), **invalid properties**, **missing event_id**, and **update failed**. The `review-event-note-problems` command (“Review Event Note problems”), the scan notice's **Review and fix** link, a **⚠ N note problems** toolbar button shown only while problems exist, and **Review and fix…** under Settings → Event Note diagnostics open the same review dialog. Settings also keeps the plain-text list under **Show as text** for issue reports.

Each card first says which event the problem affects (title, date and time in the display zone, and calendar; a removed subscription is named from History) and whether the calendar currently shows it, then lists every note that links to the notes involved: the Daily Note entries for the event, quoted, and any other note with a resolved link. The single-note card says that trashing leaves those links pointing to a missing note while keeping it as an ordinary note keeps them working; a duplicate's outcome list warns when a note to be trashed still has links that will not be moved to the kept note. The dialog shows one card per problem with a plain explanation, filter chips per kind, and the notes involved side by side: path, modification time, badges for the recommended note and for notes the calendar link or the Daily Note entry points to, properties (start and end in the display zone; values that differ from the kept note highlighted), and the body with lines the kept note lacks highlighted, plus an optional line-by-line diff. For a duplicate the user picks the note to keep (preselected: the linked note, then the one the Daily Note lists, then the one with the most text; for copies of a reconnected note, the note that now holds the event) and, for each other note, **Move to trash**, **Add its text to the kept note, then move to trash** (appended under a `## Merged from <name>` heading, without its title heading), or **Keep as an ordinary note**. Exact copies default to trash; notes with their own text default to staying as ordinary notes. Before applying, the card lists what will happen to each file and warns in red when trashing would lose text or properties the kept note does not have. A bulk button moves every exact copy to trash: identical to its kept note byte for byte, or, for copies of a reconnected note, apart from event properties. Single-note problems offer **Open note to edit**, **Refresh calendars** (not in calendar), **Belongs to “<calendar>”** (removed calendar matched by several), **Restore last valid properties** (invalid or missing `event_id` while the last valid version is still known and the YAML can be read), **Keep as ordinary note**, and a two-click **Move to trash**.

Every fix rereads its notes and refuses to write if any changed since the dialog displayed them. Property removal and merged text are committed through the recovery journal; trashing uses Obsidian's configured trash afterwards, so a failed trash leaves an ordinary note, not a duplicate. Keeping a note other than the linked one rewrites the Daily Note entry to the kept note in the same way as **Change…**. Releasing a note removes only Calendar-Note's link to it; its Daily Note entry and text stay. The dialog rescans after each fix and also updates while open when notes are edited. The service operations have automated coverage; the dialog was checked only in a browser rendering with sample notes, not in native Obsidian.

Date patterns use Moment formatting and the configured IANA display zone (default `Asia/Taipei`). Daily Notes follow enabled core Daily Notes settings, then Calendar-Note fallback settings. Weekly Notes prefer enabled Periodic Notes weekly configuration, then Calendar plugin weekly configuration, then Calendar-Note fallback settings. Detection uses internal Obsidian provider state because there is no public provider API; provider upgrades may change those internals. Templates are Vault-relative Markdown paths with `{{date}}` and optional `{{date:FORMAT}}` replacement. Event Note patterns additionally accept `{title}`, `{calendar}`, and `{uid}`, and may start with a `{daily}` segment that stands for the folder of the event's Daily Note (the Daily Note path for the event's calendar date without its file name). For example, with Daily Notes at `Journal/YYYY/MM/YYYY-MM-DD`, the pattern `{daily}/{title}` files an October 23, 2026 event as `Journal/2026/10/<title>.md`. `{daily}` is inserted after Moment formatting, so folder text is never read as date tokens; it is accepted only as the first segment and must be followed by `/` and the rest of the path. With **Move Event Notes when dates change** on (`moveEventNotes`, the default), when an event's time changes (dragged or edited in the calendar, its `start` edited in the note, or a subscription update), an Event Note that is still where the pattern placed it moves to the pattern's path for the new time, so with `{daily}` it follows the event to the new Daily Note's folder. The note keeps its name if the user renamed it, takes a ` (2)`-style suffix if the target is taken, and is not moved if the user moved it out of the pattern's folder or linked a different note with **Change…**. The link records the time the note was placed for (`placedAt`); links saved before this change fall back to the note's own `start`. The move is recorded as `moveTo` in the same commit as the date change, then carried out afterwards with `fileManager.renameFile`, so Obsidian updates links to the note and the existing rename handling rewrites the Daily entry. A failed move is reported once and leaves the note and its link where they were. With the setting off, no move is recorded, and moves recorded before it was turned off are cleared without renaming; the Daily entry still follows the event. Changing the pattern or Daily Notes settings alone does not move notes. Moves have automated coverage only; they have not had native QA. The Event Note Properties setting offers Follow Obsidian, Collapsed (default), and Expanded, applied as the initial display state when a recognized Event Note opens. Users can toggle Properties afterward. The implementation depends on Obsidian's editor DOM/CSS behavior; it does nothing when the native property panel is unavailable or hidden, and may need adjustment if Obsidian changes its selectors.

Subscriptions accept HTTPS and `webcal://` feeds. The plugin converts `webcal://` to HTTPS, uses conditional requests when available, parses feeds with `ical.js`, caches the response privately, and does not write to the upstream calendar. A UTF-8 BOM before `BEGIN:VCALENDAR` is accepted. Timed events without `DTEND` or `DURATION` are retained as zero-duration events; short source intervals are also retained. The 15-minute minimum applies to local creation and manual editing or rescheduling of any event, including imported events. Recurrence instances are identified by source, UID, and original RECURRENCE-ID. Imported event rescheduling is local-only. Source changes can update managed Event Note times and the tracked Daily Note bullet, while preserving note body and unrelated journal content. History tracks accepted changes and supports review, eligible retry, and explicit resolution of local overrides. A durable recovery journal preserves prior committed state and pauses edits when interrupted writes require recovery. There is no automatic deletion of notes when events are cancelled or removed from feeds.

### Subscription troubleshooting

An ICS URL can work in iOS and fail here because clients may support different valid iCalendar forms. Before the current parser updates, feeds containing multiple complete `VCALENDAR` streams and `RDATE;VALUE=PERIOD` recurrence values exposed compatibility gaps. Automated parser fixtures now cover these forms; native UI rendering has not been verified for the new parser changes. Delta objects sent with `METHOD:CANCEL` are unsupported, whether or not they include event times. They should report a specific error rather than be applied as a full subscription snapshot that could remove unrelated imported events. This does not change handling of `STATUS:CANCELLED` inside a complete snapshot. The specific feed reported by the user was not provided, so its contents and provider behavior have not been inspected and these known pre-fix gaps are possible causes, not a diagnosis.

Use the source's displayed diagnostic category to narrow down the problem: body or syntax errors indicate the response could not be parsed as iCalendar; semantic UID, time, range, limit, or timezone errors indicate parsed data failed validation; network and HTTP errors report request failures; empty and `304` cache outcomes describe feeds without importable events or unchanged cached content; write errors indicate local sync/storage failure. A write failure should not be reported as invalid ICS. When reporting an issue, share the diagnostic category, provider name, and a redacted structural example if possible; never include a private subscription URL or raw calendar payload.

Earlier native subscription QA for the committed ICS fixes passed in Obsidian 1.14.5 on macOS using a dedicated test Vault and the then-final ZIP. It verified a public Google Taiwan holiday feed, rapid URL/Enabled changes, URL clearing and blank-source behavior, a controlled UTF-8 BOM feed with a zero-duration and normal event, and sanitized Settings status/cache retention after an injected HTML response. The main-calendar failure banner was not inspected natively and its visibility has source and unit-test coverage only. The current parser compatibility and diagnostics changes described above have not yet received test or native QA results. The user's exact feed remains unverified because its URL was not provided.

## Automated checks and controlled feed testing

Run `npm run typecheck` and `npm test` before packaging. Tests cover date/week rules, provider setting resolution, note/path handling, ICS parsing, subscription refresh behavior, source reconciliation/history, and storage recovery. They run against test adapters and fixtures; they do not prove behavior in an installed Obsidian app.

For controlled subscription testing, use a private local HTTPS fixture server or an HTTPS test endpoint that you control. Add its URL as a source in the test Vault, and use deterministic ICS fixture revisions for baseline, changed time, unchanged revision metadata, cancellation, recurrence override, invalid feed, and recovery cases. Avoid putting real calendar URLs or payloads in repository fixtures. Confirm manual Refresh and scheduled refresh, conditional fetch/cache retention, recurrence expansion, all-day exclusive end dates, time zones/DST, and independent behavior when one source fails. For source-change tests, compare the event view, managed Event Note fields, the exact tracked Daily Note bullet, unrelated journal content, and History before and after. Test local override resolution, Retry eligibility, source supersession, changed or ambiguous recurrence identity, and interrupted write recovery.

## Native Obsidian test-Vault checklist

Native QA was completed for the scenarios below in an isolated Vault with Obsidian 1.14.5. The build was copied into the Vault as `main.js`, `manifest.json`, and `styles.css`; the plugin loaded, registered its commands, and opened the Calendar-Note view. This does not establish every acceptance criterion.

Verified in Obsidian 1.14.5:

- Creating a local event created its Event Note and Daily Note bullet immediately. With core Daily Notes enabled and its folder setting blank, the Daily Note was created at the Vault root as `YYYY-MM-DD.md`.
- Rescheduling a local event across days preserved custom YAML properties and note body, retained the past-date journal, and moved only the tracked event link to the new date's Daily Note.
- Clicking an empty main-calendar date header opened that date's native Daily Note without creating an Event Note.
- A controlled subscription test passed an ICS feed into the actual parser and source-sync path. Changing an event from the 23rd to the 24th retained its Event Note path and body and moved its Daily Note link.
- Injecting a Daily Note write failure during a change from the 24th to the 25th rolled back the note/cache update and persisted a pending review row.
- After plugin reload, the pending 24th-to-25th change remained available. Retrying reused the same history ID, applied the new time and moved the Daily Note link; marking the row reviewed persisted.
- Native editor QA opened `Weekly Notes/2026-W43.md`, and typed content autosaved. With no user template, the note contained `## Weekly review` and no generated H1. A final reload preserved the edited Weekly Note text and reviewed state.
- A live `requestUrl` request to the public `https://raw.githubusercontent.com/kewisch/ical.js/master/samples/minimal.ics` fixture parsed one event and its `VTIMEZONE`. The event was unlinked, so the Vault file count remained unchanged; the source was disabled after the check.
- Imported Event Note renames through Obsidian's file manager passed both with automatic internal-link updates enabled and with the “Do not update” prompt choice. Each left one valid managed Daily Note bullet, removed the old bullet, cleared pending rename state, retained the stable event ID and new path, and preserved Event Note body and unrelated journal text. Saved state agreed, and no recovery journal remained. A second reload preserved links, `reviewedAt`, source-times resolution history, and native-edited Weekly Note text.
- Native UI inspection confirmed the Month/Year date control is a single clickable date with no overlap, Week labels are single-line English abbreviations with no redundant week row, and the full-width event-title field is focused and defaults to today.
- Calendar opening QA confirmed both commands create fresh leaves and keep the active Event Note open: `open-calendar` opens a new tab, and `open-calendar-right` opens a separate right split beside the note. A plain ribbon click opens a fresh tab in its group; Cmd-click opens a right split. Both commands are available for user-assigned hotkeys and have no default bindings. Native testing exercised Cmd-click on macOS; Ctrl-click is covered by the platform-independent modifier logic tests.
- Event Note Properties behavior passed in source and reading modes: Collapsed applies when an Event Note opens, a manual toggle to expanded remains in effect after 450 ms, reopening the same Event Note reapplies Collapsed, and ordinary notes remain expanded. Expanded also remains selected after reopening; Follow Obsidian preserves the native state without adding Properties observers. A same-path note without a nonblank `event_id` is treated as ordinary even if the plugin previously recorded its path as an Event Note.
- A fresh Event Note whose basename matches its event title contains only `event_id`, `start`, and `end` frontmatter, with no generated H1 or extra body headings.
- The `remove-duplicate-event-note-title` command removed a leading H1 exactly matching the active recognized Event Note's basename while preserving frontmatter (including its owner property) and the remaining body. Running it again left the file byte-for-byte unchanged. Recognition requires a nonblank `event_id` and valid start/end interval; it was unavailable on an ordinary same-path note without `event_id`.

Source-resolution QA confirmed that a local override remains effective when the source baseline changes; **Use latest source times** clears the override, applies the accepted interval, moves the managed Daily Note bullet, preserves Event Note body, and records a separate resolution-history row. An identical source snapshot caused no revision increment, history row, or linked-note write. Editing Event Note frontmatter directly retained event identity, established a local override, and a rescan moved the managed Daily Note bullet while preserving custom YAML and body. A controlled Daily Note write failure rolled back note/cache changes and persisted a review row; after reload, retry reused the same history ID and applied the new time, and marking it reviewed persisted. A controlled 23rd-to-24th source change retained the Event Note path/body and moved its Daily Note bullet.

The automated suite and `npm run typecheck` are the repeatable checks for the current source. The legacy browser-preview suite passes all five test files with the preview-local CommonJS package scope. Automated checks and library-level callback tests do not establish native drag behavior or narrow-window layout.

Native UI checks confirmed the sidebar and main calendar fill available height and bottom-align with mini-calendar content; centered English date labels remain single-line without duplicates through All days → Workdays → All days and Week → Month → Week; pointer and keyboard resizing work; and sidebar width, collapsed state, Workdays setting, and Week view persisted through reload. Record additional Obsidian version, OS, test Vault description, fixture IDs (never private URLs), and pass/fail notes here as QA continues. Native behavior outside the verified scenarios above remains unverified.

Known display behavior and constraints: Calendar-Note uses English abbreviated labels for calendar chrome regardless of note locale, with main date headers kept on one line (for example, `Sun 18`). The sidebar mini-calendar can show adjacent months when the available height permits. Moment locale and week rules still control date formatting and week identity.

New-note heading behavior: the no-template Daily Note fallback begins with `## Journal`, and the Weekly Note fallback begins with `## Weekly review`, without generated H1 headings. A new Event Note omits a title heading when its actual basename matches the original event title; otherwise it starts with an H1 containing the original title. Without a user template, its body has no automatically added `Notes` or `Follow-up` sections. The `Calendar-Note: Remove duplicate Event Note title` command is available only for an active recognized Event Note and removes only a leading H1 that exactly matches its basename. It preserves frontmatter and all remaining body text. Existing notes and user-provided templates are preserved; the command is opt-in and there is no automatic mass migration.

## Browser prototype

The preview directory has its own CommonJS package scope so its legacy UMD scripts and tests remain CommonJS while the plugin project uses ESM. Run `node --test docs/changes/calendar-note/preview/*.test.cjs docs/changes/calendar-note/preview/smoke-test.cjs` to run the five legacy preview test files. To view the older browser-only prototype, run `python3 -m http.server 4318` from the repository root and open `http://127.0.0.1:4318/docs/changes/calendar-note/preview/index.html`. Its controls demonstrate interaction design using local browser storage and sample data. They do not exercise Vault writes or network subscriptions.
